The pipeline

One query. A grounded answer, or a refusal.

A language model is excellent at turning a question into SQL, and should never be trusted with the arithmetic. So it isn't. The model writes the query having never seen a row; a read-only database returns the rows; a verifier confirms every number in the prose actually came from them. 

question
   ├─ plan      model writes SQL, having never seen a row of data
   ├─ guard     parsed, SELECT-only, allow-listed, LIMIT enforced   ← refuses here
   ├─ execute   read-only connection                                ← refuses here
   ├─ narrate   prose written, then every number checked against the rows
   ├─ lineage   SQL + tables + columns + row count + result hash
   └─ audit     appended to a hash-chained log

The four guarantees

A claim is only worth what enforces it.

Each guarantee is backed by a mechanism and a test that would fail if it broke, not by a promise.

The model can't write to the database

A connection opened readOnly: true; the database refuses writes below anything the code can reach.

Only SELECT, only allow-listed, always bounded

guard.js parses SQL to an AST and inspects the full table list, including subqueries and CTE bodies.

Every figure came from the data

grounding.js extracts each number and matches it to a returned value, allowing only legitimate transforms.

A past answer can't be altered unnoticed

audit.js hash-chains each entry to the one before it; verify() reports the first index where the chain breaks. Optional Ed25519 signing and an external anchor extend this to a full rewrite of history.

How the proof works

Two hashes, doing two different jobs.

Keeping them separate is the whole point. One proves the answer reproduces from the data; the other proves the record of what was asked and answered hasn't been edited since.

The result hash

Does the answer reproduce? Computed over the rows the database returned, in a canonical form (stable row order, stable formatting). Re-run the same SQL at the same as-of date against the same snapshot and you get the same hash; a different hash means the data, the query, or the as-of date changed. The question is deliberately not part of it, because the same question can yield different SQL on different days. This is what an auditor recomputes.

The entry hash

Was anything edited? Every query is written to an append-only log; each entry records the question, the SQL, the result hash and the grounding verdict, and each entry's hash includes the hash of the one before it. Edit or drop any past entry and its hash changes, the next entry's link no longer matches, and every entry after it fails verification. The log is tamper‑evident, not immutable: it makes changes detectable, not impossible.

A plain chain has one gap: whoever can write the whole file could rewrite every entry from an edit point onward. Two optional layers close it, Ed25519 signing (a rewrite now needs the private key) and an external anchor that publishes each checkpoint hash somewhere outside your control. The anchor need not be a blockchain: WORM storage, an RFC 3161 timestamp, or simply handing the checkpoint to the auditor all work; a public chain is only for the trust‑no‑one case.
