Try your own SQL — watch the guard refuse what it should

The guard parses the SQL, allows only SELECT over allow-listed tables and columns, and injects a LIMIT. The payroll table and vendors.tax_id are deliberately outside the allow-list, so a query that reaches for them is refused with a reason — the same control the agent skill runs behind.

What just happened

Your question was mapped to one named query with parameters; the query ran through the guard on a read-only connection; the automatic checks confirmed the result is internally consistent; and the answer sentence was filled only from values the database returned. The result hash lets an auditor re-run the query and compare; the audit entry is appended to a hash-chained log, so Verify the audit chain reports the first entry that was ever altered. In the agent skill, Claude does the mapping step through run_canonical, and for open questions the guarded planner writes the SQL; nothing after that step changes.
