Civic-Chain · vendor & security

Built so your ledger never leaves the machine you run it on.

The Auditor is a tool for proving where public money went. It would be a poor one if the act of using it quietly shipped that money's records somewhere else. It does not. This page is the procurement-ready account of what runs where, what leaves the machine and what never does, and how you verify the parts you are asked to trust, yourself.

Data residency

What runs where

The engine, the database, and the audit log all live on the machine you run the Auditor on. There is no Civic-Chain service in the data path.

No telemetry

The package phones no home, reports no usage, and sends no analytics. Installing or running it opens no connection to Civic-Chain.

No servers in the data path

The credential-free tools (run_canonical, run_query, verify_answer, run_control, verify_audit, CSV import) make no network call at all.

You choose the only subprocessor

A free-text question that needs a query planner calls the model provider you configure with your own API key, and nothing else leaves the machine. No key, no model call.

Read-only by construction

Every query is parsed, held to a per-warehouse table and column allow-list, and refused unless it is a single read-only SELECT. The guard is the trust boundary.

Sensitive data

PII is withheld by the allow-list, not by good intentions

Each warehouse ships an allow-list that names the exact tables and columns a query may read. Anything not on it, policyholder SSNs, client contacts, donor histories, student records, employee payroll, is unreachable: a query that reaches for it is refused with table_not_allowed or column_not_allowed before it runs. The refusal is the feature. You can watch the guard turn down those requests in the live demo.

Supply chain

How the package reaches you

Published with provenance

The engine ships as @civic-chain/auditor on the npm registry, built with npm provenance so the published artifact ties back to the source commit and the build that produced it.

Runtime

Node.js 22+. The query path uses the built-in node:sqlite, so the SQLite engine is the runtime's, not a bundled native binary. The package ships no compiled binaries.

Local install check

npx @civic-chain/auditor doctor verifies the runtime, builds the bundled demo locally, and prints the MCP config. After the install itself it makes no network call, runs no subprocess, and reads no credential.

Source-available

The source is published for inspection under the Civic-Chain Commercial Licence. You can read every line that handles your data before you run it.

Verify, don't trust

Confirm the ruleset signing key yourself

Signed rulesets are signed with an Ed25519 key held offline. The matching public key ships with the package so you can verify any ruleset's signature and pin the key you trust. Recompute the fingerprint and confirm the key you have is the key we publish:

Public key
auditor-core/assets/civic-chain-ruleset-pub.pem
Key id
acb80e87885da931 (first 16 hex of the SPKI DER SHA-256, recorded on every signed entry as signedBy)
Fingerprint
acb80e87885da9317ae908d39f0f050a4da5ca6f72e8e547870cbed6e271a5bc
openssl pkey -pubin -in auditor-core/assets/civic-chain-ruleset-pub.pem \
  -outform DER | openssl dgst -sha256

A ruleset whose signedBy does not match this key id was not signed by Civic-Chain; treat it as untrusted. The private key is never committed and never leaves an offline machine.

Disclosure

Reporting a vulnerability

Email info@civic-chain.com with “SECURITY” in the subject. Include what you found, how to reproduce it, and the version or commit you were running. We acknowledge every report and work with you on a fix. Please do not open a public issue for a security problem. For encrypted disclosure, say so in your first message and we will arrange a key.
